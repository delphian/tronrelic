## Why This Module Exists Separately

Analytics keyed off the cookieless `tronrelic_tid` is independent of identity — it survived the Phase 6 removal of the legacy UUID system untouched. The `traffic_events` ClickHouse table captures two complementary streams without touching identity storage: server-recorded `bootstrap` first touches (cookieless, so crawlers/unfurlers/probes are included by design) and client-recorded `page` navigations (the interactive clickstream of cookied and registered visitors). One table, differentiated by `event_type` and `user_id`, so a visitor's journey from anonymous first touch through registered browsing stays in one place.

Physical storage names are unchanged from when this code lived under the user module: the GSC collection is still `module_user_gsc_queries`, and the ClickHouse migrations' `id` fields are unchanged. Only their migration `qualifiedId` shifts from `module:user:*` to `module:traffic:*` because the scanner derives it from the directory; both migrations are idempotent (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`), so re-execution under the new id is a safe no-op.

## Metrics Contract

Canonical definitions every dashboard, query, and AI tool must conform to. Metric drift happens when definitions live implicitly in SQL — this section is the source of truth; change it and the code together.

| Metric | Definition |
|--------|------------|
| Visitor | Distinct `candidate_uid` (the `tronrelic_tid` cookie) that emitted at least one `page` event in the window — a client that ran JavaScript. This is the canonical Unique Visitor rule: cookieless bots never run JS, so requiring a page event drops them from every visitor metric by construction, independent of `bot_class` (it is also the "no-JS" bot signal). Reads scanning `page` rows express it inline as `uniqExactIf(candidate_uid, event_type = 'page')`; the remaining `bootstrap`-only read (campaigns) ANDs in the `pageVisitorMembership` subquery; the session-scoped acquisition reads (sources/landing/source-details) get it structurally, since only `page` rows sessionize; `new-users` enforces it via a window-scoped `HAVING countIf(event_type = 'page' AND <in-window>) > 0` (scoped to the window so a page beacon after a custom range's end cannot retroactively qualify a new visitor). Still per-browser, not per-person: cookie clearing and multi-device use recount the same person. Bootstrap-only tids stay visible in the Crawlers-tab `bot_class` breakdowns — they are simply not *visitors*. |
| Pageview | A `page` event — the client-side navigation beacon. `bootstrap` rows are first touches, not views (the middleware bootstrap and the first page beacon record the same navigation); every "views" figure counts `page` events only. |
| Source / landing page | **Session-scoped** on the Analytics tab: one derived session that *starts* in the window contributes one entry — its first `page` hit gives the landing path, and that hit's `original_referrer` gives the source. A visitor returning three times contributes to each thing that brought them back, so `count` is a session count. The dashboard panels still *display* `visitors` (`uniqExact`) per the visitors-primary convention, so returning through the same source does not increment the rendered figure — session-scoping widened which sources appear, it did not change the displayed unit. Self-referral sessions — an entry hit whose referrer is this site, i.e. a visitor resuming past the 30-minute gap — are **excluded** from both panels: a resumed tab arrived from nowhere, so it has no source and nobody landed on it. GA4 would count them as `direct`; at this volume that is not a rounding error (a 30-day sample had 235 of 767 sessions as continuations from **nine** visitors, enough for two idle dashboard tabs to outvote 159 genuinely-referred people). Those sessions still count wherever a session count is legitimately a session count — engagement, duration, bounce. **Read the `original_referrer` column, never `referer`:** on a `page` row `referer` is the beacon XHR's own header — always the current page URL — so grouping by it collapses every session to a self-referral. The Visitors tab is different by design: its per-row acquisition stays first-touch (the tid's earliest row, whenever that was) so a row explains where that visitor originally came from. |
| Channel | `classifyChannel` over first-touch referrer + UTM + ad click-IDs (`services/channel-classifier.ts`). Paid signals win over referrer heuristics (a paid Google ad carries a google.com referrer, and an auto-tagged one carries only `gclid`). Stored at write time in `traffic_events.channel` on `bootstrap` rows only — `page` rows carry the site's own origin as referrer and store NULL. |
| Session | Derived at read time from `page` events: a per-tid run of hits with gaps under 30 minutes (industry-default rule; `SESSION_GAP_SECONDS`). Never stored — the definition lives in `TrafficService.derivedSessionsSql` only. Duration = last hit − first hit; a single-page session is 0s. Attributed to the window containing its start (GA4's rule): windowed reads scan one extra gap before the window and drop sessions that began earlier, so a boundary-straddling session counts in exactly one window. |
| Bounce | Single-page derived session. Bounce rate = bounces / sessions. |
| Conversion (`converted`) | Distinct tids carrying a non-null `user_id` at any point in the window — login attribution, includes returning account holders. |
| New accounts | Distinct tids in the window attributed to accounts *created* during the window (Better Auth `createdAt`, resolved through the identity module's `'accounts'` service). Creation date is ground truth — a first-login-event proxy would re-mint long-standing accounts as "new" once their earliest rows roll off the table's 18-month TTL. Counted in visitor units so the funnel stages nest. |
| Bot filter (`bots=exclude`) | Excludes rows classified as bots; NULL (unclassified) rows are kept — "exclude known bots", not "humans only". Because a visitor must have a `page` event, cookieless non-JS bots are already absent from visitor counts regardless of this filter; its residual effect on visitor counts is limited to JavaScript-running bots the classifier caught. |
| High-volume source (annotation) | A `subnet_hash` whose in-window request count exceeds `HIGH_VOLUME_SUBNET_MIN_REQUESTS`, surfaced by `getHighVolumeSubnets` (`/analytics/flagged-subnets`) and flagged in the Visitors-tab Source column. An operator hint only — **never** excluded from any count, because legitimate shared egress (offices, VPNs, universities, mobile carriers) also concentrates real visitors behind one network. Not bot-filtered: the flag is about raw source volume, not a `bot_class` guess. |
| Ignored account (always-on) | A Better Auth account on the operator ignore list (`module_traffic_ignored_users`). Excluded from **every** read, unconditionally — no toggle. Whole-person: `setIgnoredUserIds` resolves, once per list change (bootstrap + each add/remove), every `candidate_uid` that has *ever* logged in as an ignored account — via an unwindowed `SELECT DISTINCT candidate_uid … WHERE user_id IN …` — and caches that tid set; reads then inject it as a literal `candidate_uid NOT IN (<cached tids>)`. So every tid that ever logged in as an ignored account drops out entirely — including its anonymous, pre-login rows — not just its logged-in rows. The literal is index-friendly (`candidate_uid` is the second column of `ORDER BY (timestamp, candidate_uid)`), so the costly unindexed `user_id` scan runs once per list change, not on every read. Tradeoff: **bounded staleness** — a login as an ignored account between refreshes isn't excluded until the next refresh (re-save the list, or the next boot). Read-time filter only: rows are always recorded and retained, so removing an account restores its full history to every stat immediately. Applied via `TrafficService.rangeParams` (the 18-read chokepoint) plus `getLiveVisitorCount`; the bot-focused Crawlers-tab aggregates and the source-volume `flagged-subnets` read are not filtered (no meaningful registered-user signal there). |

**Two attribution doctrines, on purpose.** *Per-visitor* surfaces are first-touch: the `tronrelic_ref` cookie is never overwritten and the Visitors tab reads the tid's earliest row, so a visitor who arrived direct and returns via a campaign link still shows "direct" — that row answers "where did this person come from". *Aggregate* surfaces (Traffic Sources, Top Landing Pages) are session-scoped, so they answer "what brought traffic in during this window" and returning visitors are visible. `campaign-performance` remains bootstrap-attributed and is the surface that still sees paid tagging, because ad click-IDs are recorded only at first touch.

## Recording the Network (ASN)

Every `traffic_events` row carries `asn`, the autonomous system number (ASN) of the network the request came from, such as a cloud provider or a mobile carrier. It answers "who operates this source", which the address hashes cannot, because the address itself is never stored. Without it, naming the network behind a burst of automated traffic meant reading raw addresses out of the Nginx access log.

Cloudflare knows the ASN of every request but sends no header for it, so a zone Transform Rule (Rules → Transform Rules → Modify Request Header) sets one:

| Setting | Value |
|---------|-------|
| Match | All incoming requests (`true`) |
| Operation | Set dynamic |
| Header name | `x-client-asn` (`ASN_HEADER` in `services/traffic.service.ts`) |
| Value | `to_string(ip.src.asnum)` |

The name cannot start with `cf-` or `x-cf-`, because Cloudflare refuses rules that write under its own prefixes. Because the rule *sets* the header, it overwrites anything a client sent through Cloudflare. `buildTrafficEvent` stores the value only when `CF-Ray` is also present, the same rule it applies to `CF-IPCountry`, and `parseAsn` accepts only a positive 32-bit decimal integer, so AS0 ("could not be placed") is stored as NULL. Bootstrap rows get the header through the Next.js middleware's `FORWARDED_HEADERS` list, and page beacons get it directly, since Nginx passes request headers to `/api` unchanged.

NULL therefore means "not recorded", never "no network": rows before migration 019, rows written before the Transform Rule existed, and requests that bypassed Cloudflare. Deploy in this order: ship the code, run migration 019 from `/system/database` (inserts carrying the field fail until the column exists), then create the Transform Rule.

## Automated-Network List

Some browser fleets defeat every per-request check: they send a stock Chrome UA, run the page's JavaScript, and hide `navigator.webdriver`, so their rows are written `human` and counted as visitors. The network they run on is the one thing they cannot hide, so an operator lists confirmed automated networks by ASN on the Settings tab of `/system/traffic`. `buildTrafficEvent` checks each request's ASN against the list through the `botNetworks` input (an `IBotNetworkLookup` the bootstrap controller is constructed with), and the classifier turns a `human` verdict into `bot_other` for a listed network.

| Rule | Why |
|------|-----|
| Labels only; never blocks | A listed network is still served every page, so a wrong entry costs miscounted rows, not lost visitors. Blocking would be a Cloudflare firewall rule, not this list |
| Write-time, forward-only | Like every classifier signal, the label is set when the row is written. Rows recorded before a network was added keep their label, and removing a network does not relabel rows written while it was listed |
| Trusted only through Cloudflare | The ASN is stored only when `CF-Ray` is present (see [Recording the Network](#recording-the-network-asn)), so a direct-to-origin caller cannot send the header to label itself or anyone else |
| Operator-confirmed, not imported | Real VPN users browse from datacenter networks too, so the list holds networks someone has checked rather than a published datacenter list. Before listing one, check its rows with the per-event AI tool (`groupBy: "asn"`) for signs of real people: logins, returning cookies, referrers, varied User-Agents |
| Redirect hits too | The edge middleware forwards `x-client-asn` and `cf-ray` on the redirect-hit beacon, so `redirect_events.bot_class` applies the list the same way. Both paths read the ASN through `readCloudflareAsn`, so the CF-Ray rule cannot drift between them |

The list is read from memory on every event; a change takes effect for the next event the backend records.

## REST Endpoints

The `/api/admin/users/traffic/*` reads below are under `requireAdmin` and accept `sinceHours` (default 24, ceiling 720) and `limit` (default 20, ceiling 200).

| Method | Path | Returns |
|--------|------|---------|
| GET | `/api/admin/users/traffic/summary` | Row counts by `bot_class` over the window (NULL preserved) |
| GET | `/api/admin/users/traffic/top-paths` | Most-hit landing paths |
| GET | `/api/admin/users/traffic/top-countries` | Most-active ISO-3166 alpha-2 countries |
| GET | `/api/admin/users/traffic/bot-other-samples` | Frequent UAs classified `bot_other` (classifier-gap feedback) |
| GET | `/api/admin/users/traffic/bot-trend` | Daily counts per `bot_class` (default `sinceHours=168`); NULL folded to `unclassified`; `human` excluded |
| GET | `/api/admin/users/traffic/bot-paths` | Top paths for one `botClass` (allow-list = `BotClass` minus `human`, plus `unclassified`; 400 on miss) |

Both back the Crawlers tab, a bot-visibility surface that serves **no** human traffic — enforced in the query and the allow-list, not the frontend series list. NULL `bot_class` is asymmetric by design: *human* to the analytics reads (`HUMAN_ROWS_FILTER`), *unknown* here, surfacing as `unclassified` so coverage gaps stay visible. `/summary` is unfiltered and still reports every class.

The `/api/admin/users/analytics/*` router (also `requireAdmin`) serves the `/system/traffic` dashboard aggregates — the unified `overview-trend` headline (current + equal-length-previous-window KPIs for delta rendering, plus a zero-filled visitors/pageviews series bucketed hourly for windows ≤ 48h and daily otherwise), the `live` counter (distinct visitors in the last 5 minutes), daily visitors, anonymous first touches (`new-users`), the high-volume source-network annotation (`flagged-subnets`), traffic sources, geo/device breakdowns, engagement, the binary conversion funnel, retention, and the GSC endpoints — all backed by `traffic_events`. Every windowed analytics read accepts `bots=exclude` to restrict counts to human-classified rows (`bot_class = 'human'` or legacy NULL) — referrers are client-supplied and routinely spoofed by crawlers, so the default include-everything counts overstate real audiences; the dashboard's global filter defaults to humans-only. The `traffic-sources`, `top-landing-pages`, `geo-distribution`, and `device-breakdown` buckets carry `visitors` (distinct tids, the primary measure per analytics convention) alongside the raw event `count`. `traffic-sources` and `top-landing-pages` are session-scoped: they sessionize `page` rows and group one entry per session starting in the window, so returning visitors are counted and `count` reports sessions. Sessionizing is what keeps landing pages from degrading into most-viewed pages, and the source read takes `original_referrer` (the browser's real `document.referrer`, forwarded by the beacon) rather than the `referer` header of the beacon request itself. Sessions resumed after the gap (self-referrer) are excluded as non-arrivals — see the Metrics Contract. One tradeoff: the write-time `channel` column lives on `bootstrap` rows, so these buckets classify by referrer domain only and an auto-tagged paid click reads `organic`. The `conversion-funnel` response carries `converted` (tids logged in at any point in the window — includes returning account holders) and `newAccountVisitors` (tids attributed to accounts created during the window — Better Auth `createdAt`, composed by the controller through the `'accounts'` registry service; 0 when identity is unavailable). `traffic-source-details` (the expansion under a Traffic Sources row) shares the aggregate's cohort exactly — same `sessionSourceExpr` and self-referral filter — and breaks those sessions down by their entry hit's path/country/device/UTM, with percentages over the session count. It must stay in lockstep: while it was first-touch under a session-scoped aggregate, a visitor acquired direct who returned from Google counted in the Google row but had no in-window Google `bootstrap` row, so the panel rendered empty beneath a non-empty row. Its UTM table is sparse by nature, since tagging is recorded only at first touch. `campaign-performance` remains first-touch attributed: `bootstrap` rows define each campaign's cohort, and conversions read the cohort's full in-window clickstream. GSC reads expose the keyword cache: `gsc/keywords` (aggregated clicks/impressions/CTR/position for a `periodHours` window, plus `windowStart`/`windowEnd` carrying the whole UTC days actually covered — the window ends on the newest day in `module_user_gsc_daily_totals`, not at a fixed "now minus 3 days", because Google often finalizes a day later than that and a fixed offset leaves `24h` sitting on an undelivered, empty day) and `gsc/keywords-by-day` (zero-filled daily buckets for trend charts; per-day totals come from `module_user_gsc_daily_totals` because GSC omits anonymized queries from keyword rows). Every GSC read also returns `firstIncompleteDate`, the first day in its window Google has not finalized (null when all are final), and each `keywords-by-day` bucket carries `preliminary: true` from that day on. `gsc/pages` (same window shape) aggregates the [page, date] totals in `module_user_gsc_page_totals` — a query-less fetch that escapes anonymization, so it accounts for clicks no keyword row can and surfaces zero-click-but-impressed pages. All are Mongo-backed and return empty/zero until the `gsc:fetch` job has stored data. The frontend consumes everything through `src/frontend/modules/traffic/api/client.ts`.

The per-visitor surface lives on the same router. `visitors` is the Visitors tab's single read: one row per tid meeting the Visitor rule in the window, keyed on `candidate_uid` and carrying first-touch acquisition (channel, referrer domain, landing page, UTM, subnet hash, ip hash — resolved from the tid's earliest row *whenever* that was, so a returning visitor still shows its original source) alongside in-window behaviour (`page` views, distinct paths, last path) plus `isNew`, `accountId`, `botClass`, and `userAgent`. The UA is *latest* in-window, not first-touch, because `device` and `botClass` derive from it and read that row — pairing a first-touch UA with a latest-row device lets the panel contradict itself for a visitor who switched machines. The two hashes are read together: `subnetHash` answers "same network?", `ipHash` separates clients inside one office, VPN, or carrier that the subnet collapses. Raw IPs are never stored. It deliberately carries **no** per-visitor session count: the derived-session join is the most expensive part of the read and the figure earned nothing at row level — session KPIs live on the Analytics tab, where they are aggregates. An optional `accountId` narrows it to every tid that account has ever browsed under — the per-account rollup a tid-keyed table cannot show natively. `page-hits?subject=tid|user&id=` returns one subject's ordered page hits — "every page they hit" — and backs the row expansion.

**Why one read, not three.** This replaces `tid-activity`, `user-activity`, and the tab's use of `new-users`. Those looked like three subsets of one population but were not: new-vs-returning is a *time* property and anonymous-vs-registered an *identity* property, so the two are orthogonal and no single view could say a visitor was returning *and* registered. Two keyed on the tid while `user-activity` keyed on the account, and the bot filter reached only `new-users` — `getPageActivity` took no bot parameter at all. Collapsing to one tid-keyed read makes both distinctions row attributes, gives the bot filter one application point, and surfaces `botClass`/`channel`, which are stored on every row and were previously displayed nowhere. The cost, accepted deliberately: one account browsing from three browsers is three rows sharing an `accountId`, because the tid is the unit a Visitor is defined in and the only key an anonymous row has. `new-users` survives as an endpoint because `getNewVisitors` still backs the `tronrelic-get-new-visitor-origins` AI tool.

The ignore list is managed on the same router: `GET/POST /ignored-users` and `DELETE /ignored-users/:userId` read and edit `module_traffic_ignored_users` (each mutation refreshes `TrafficService`'s cached id set so the always-on exclusion takes effect at once), and `account-search?q=` resolves accounts to add — an exact Better Auth id via the `'accounts'` service's `getAccount`, otherwise an email/name substring via `listAccounts`. See the "Ignored account" row in the Metrics Contract for the exclusion semantics.

### Sharing the Ignore List

Other components that count visitor activity, such as the `resource-markets` plugin's affiliate impressions and clicks, must leave out the same people the dashboard does. The module publishes `'traffic-ignore-list'` (`ITrafficIgnoreList`) for that. It is read-only, so the list can still only be changed from `/system/traffic`. Resolve it per request with `services.get('traffic-ignore-list')` and call `isRequestIgnored(req)` from a route handler, or `isIgnored({ userId, tid })` when the caller already holds the identifiers.

Both methods answer from the same in-memory sets `setIgnoredUserIds` maintains, so a check costs two set lookups and no database read. The user id is matched against the account list directly, and the tid against the resolved whole-person set, so the rule matches the dashboard's: a browser that has ever logged in as an ignored account is matched on its anonymous requests too. The staleness is the same as well. A browser first logging in as an ignored account after the last refresh is matched only while logged in until the next refresh.

A consumer that counts into pre-aggregated totals can only skip the visitor when the event arrives. Unlike the dashboard's read-time filter, that is not retroactive: events counted before an account was added stay counted, and events skipped while it was on the list do not come back when it is removed.

URL redirects are managed on their own admin router (`requireAdmin`): `GET /api/admin/redirects` lists every rule, `POST` creates one, `PATCH /:id` patches (e.g. toggle `enabled`, retarget), `DELETE /:id` removes. The public `GET /api/redirects` (no auth) returns only enabled rules in the minimal `{ pattern, isPrefix, destination, permanent }` shape, most-specific-first, with a 60s `Cache-Control` — it is the feed the Next.js edge middleware polls and caches to issue the actual 301/302. Redirect rules are DATA, never deployed code: an operator adds a rule from `/system/traffic` → Redirects and the middleware serves it within a minute, no rebuild.

Redirect analytics ride the same routers. `POST /api/redirects/hit` (public, no auth, rate-limited at 300/min per IP) is the fire-and-forget beacon the edge middleware fires — via `event.waitUntil`, so the 301/302 never waits — when it serves a redirect; the controller classifies the request for bots and writes one `redirect_events` row (raw hit, not tid-keyed). **Provenance is proven by matching, not a shared secret:** the beaconed `pattern` must name a currently-enabled rule (`RedirectService.getActiveRules()`) — the middleware only fires after serving one — and `destination`/`permanent` are taken from the matched rule, never the caller. Forged/stale patterns record nothing (still 200). So all three `LowCardinality` columns (`pattern`/`destination`/`country`, the last validated to ISO alpha-2) carry only trusted values, closing both the fabricated-breakdown-row and dictionary-bloat vectors an arbitrary caller would otherwise open. `GET /api/admin/redirects/analytics` (`requireAdmin`) serves the Redirects-tab panel: it accepts the same `period`/`startDate`/`endDate` + `bots=exclude` vocabulary as the analytics dashboard and returns a headline total with a human/bot split, a zero-filled hits-over-time series (hourly ≤ 48h, daily otherwise — mirrors `overview-trend` bucketing), and a per-pattern breakdown of which legacy URLs are still hit. The read is standalone (NOT `rangeParams`) because `redirect_events` carries no `candidate_uid`, so the ignore-list filter does not apply.

Two public ingestion endpoints (no auth) write rows; both resolve the tid from the unsigned `tronrelic_tid` cookie and attribute to the Better Auth account when one is present:

- `POST /api/user/bootstrap` — one first-touch `bootstrap` row. Called server-to-server by the Next.js middleware, so it captures cookieless bots and crawlers; this is the noise that powers the "Anonymous First Touches" table.
- `POST /api/user/track` — one `page` row per navigation. Called by the client-side route-change beacon (`src/frontend/modules/user/components/PageViewTracker`, via `lib/pageBeacon`), which fires on mount and every soft navigation. Bots that do not run JS never reach it, so the `page` stream is interactive-traffic-only. The body carries `landingPath`, `originalReferrer`, and `automated` (true when `navigator.webdriver` is set); only a strict boolean `true` is honoured.

The Next.js middleware matcher (`src/frontend/middleware.ts`) excludes `/images/`, so static assets such as the web app manifest never reach `/api/user/bootstrap`. Browsers fetch the manifest without cookies, and before the exclusion every page load recorded an extra `bootstrap` row under a freshly minted tid.

When ClickHouse is unavailable every read returns empty with `clickhouseEnabled: false` rather than failing.

## AI Tools

Eight read-only tools let a model answer analytics questions, and diagnose unusual traffic event by event, without an operator opening the dashboard or querying ClickHouse by hand. They register on the core `'ai-tools'` registry under provider id `traffic` via the `watch()` pattern (the ai-tools module publishes its registry during `run()`, so a one-shot `get()` would race boot order). Registration failures are logged and swallowed — this module also owns the public ingestion endpoints every page view depends on, so optional AI capability must never take it down.

Every aggregate tool conforms to the [Metrics Contract](#metrics-contract) above; the descriptions restate the Visitor / Pageview / Session definitions so the model does not invent its own. Each windowed aggregate tool defaults `excludeBots` to true, matching the dashboard's humans-only default. The per-event tool is the exception on both counts: it returns raw rows of every bot class, because automated traffic is usually what it is used to find, and labels every response `not visitors`.

| Tool | Backing reads | Capability |
|------|---------------|------------|
| `tronrelic-get-traffic-overview` | `getOverviewTrend`, `getLiveVisitorCount`, `getEngagementMetrics` | read / internal / untrusted |
| `tronrelic-query-traffic-breakdown` | sources, landing pages, geo, devices, campaigns, source-details (one `dimension` enum) | read / internal / untrusted |
| `tronrelic-get-audience-behavior` | `composeConversionFunnel`, `getRetention`, `getDailyVisitors`, plus identity's `countAccounts`/`countDistinctOwners` | read / internal |
| `tronrelic-get-new-visitor-origins` | `getNewVisitors`, projected | read / internal / untrusted |
| `tronrelic-get-crawler-activity` | bot-class breakdown, trend, paths, unclassified UAs, `getTopPaths`, `getTopCountries` | read / internal / untrusted |
| `tronrelic-get-seo-performance` | `GscService` keywords, pages, keyword→page pairs, keywords-by-day, status | read / internal / untrusted |
| `tronrelic-get-redirect-analytics` | `getRedirectAnalytics`, `RedirectService.listRules` | read / internal |
| `tronrelic-list-traffic-events` | `listTrafficEvents` (view `events`), `getTrafficEventSources` (view `sources`, grouped by `ip`, `subnet`, or `asn`) | read / **secret** / untrusted |

**The per-event tool.** It exists because the aggregates hide the pattern a diagnosis needs: browsers arriving in pairs, or one source walking the newest posts every few hours, only shows up row by row, and finding it used to take an SSH session and hand-written ClickHouse queries. View `sources` answers "who is sending the most" with one row per client, network, or operator, carrying its spread (distinct tids, addresses, networks, paths) and sampled detail (countries, ASNs, bot classes, the commonest User-Agent). View `events` lists the rows, filterable by `eventType`, `ipHash`, `subnetHash`, `asn`, `botClass`, `tid`, `pathPrefix`, and `country`, newest or oldest first, paged with `offset` up to 5,000. Paging is stable only when two things hold: the sort breaks timestamp ties on `candidate_uid`, the table's second sort-key column, so rows sharing a millisecond keep one order across queries; and the model pins the window by sending the first page's echoed `windowStart`/`windowEnd` back as `startDate`/`endDate`, since a `period` window ends at "now" and rows arriving between calls would otherwise shift every newest-first offset. The tool description says so. Both go through `rangeParams`, so the ignore list and the country scope apply, and both share one `eventFilterClause` so a filter selects the same rows in either view. Every filter is bound as a parameter and re-validated in the handler; a hash must be 16 hex characters, a tid a UUID v4, and an ASN passes through the same `parseAsn` ingestion uses. The window stops at 30 days, like the other raw-row reads. Rows are reshaped before they leave the service: `user_id` becomes `loggedIn`, `cf_ray` becomes `viaCloudflare`, and the referrer becomes a domain read from `original_referrer` on page rows and `referer` elsewhere.

**The window vocabulary mirrors the dashboard's two pickers, not one list everywhere.** The date-range tools (overview, breakdown, audience, new visitors, redirects) take the global picker's presets — `1h`/`24h`/`7d`/`30d`/`90d` — plus an explicit ISO `startDate`+`endDate` pair, and echo back `windowStart`/`windowEnd` so the model reports the window it actually got. Custom ranges matter because an operator asking "explain what I'm looking at" is often looking at one; without them the model approximates with the nearest preset and quotes figures that do not match the screen. A custom span is capped at 90 days, the widest preset, so an explicit range can never cost more than a window the model could already have named — uncapped, `getOverviewTrend` emits one fully-populated bucket per day and `composeConversionFunnel` fans out one account read per active account, both scaling linearly with a span nothing else bounds. Capping the span bounds the bucket *count*, not the payload, so the overview tool also trims: past `MAX_BUCKETS` buckets it returns the visitors/pageviews series without each bucket's top paths, countries, and sources and sets `seriesDetailTrimmed`, since a 90-day daily series carries 91 points × three dimensions × three rows. The shape survives, the dimensions stay available window-wide through the breakdown tool, and the description says so — truncate-and-point-to-detail rather than a silently enormous response. Malformed *or over-wide* range input throws rather than falling back to a preset — the opposite of the lenient REST-layer `resolveAnalyticsRange`, because a route degrading to a default window is harmless while a model that asked for March and silently got 24 hours narrates the wrong window as fact. The raw-hours tools (crawlers, SEO) keep a 30-day ceiling, matching their own tab pickers and the `sinceHours` clamp the REST layer applies to the same reads. The per-event tool takes a custom range like the date-range tools but shares the raw-hours tools' 30-day ceiling on both its presets and its custom span, because it too scans unaggregated rows.

**Parity with the tabs is the design goal, and three views exist only to hold it.** The Crawlers tab stacks the bot panels with two raw-traffic ones, so the crawler tool serves `top-paths` and `top-countries` alongside them — but they are unfiltered event-row counts across all traffic with no bot filter and no ignore-list, so the tool labels every response with a `measure` string and the description forbids reconciling them against the visitor figures. The SEO tab's keyword→page pairs panel is uncapped by design; the tool passes an explicit row cap, since `getKeywordPagePairsForPeriod` treats an omitted limit as "every pair". The Redirects tab lists rules the hit-derived analytics cannot show: a zero-hit rule — precisely the retirement candidate — appears in `view: 'rules'` and nowhere else, which is why the tool advertising "can we retire this redirect" needs both views. That view is `limit`/`offset` paged to bound the context window, not the database read: returning the inventory whole would put every rule document in front of the model at once. The read itself stays whole on purpose — the admin table and the public middleware feed both want all of it, and `listRules()` sorts on an unindexed key, so paging the query would buy no storage-layer bound while costing two extra round trips for the counts. `total`/`enabled` still count the entire inventory and `hasMore` tells the model to keep paging, so a capped page never reads as a complete list. `listRules()` breaks `createdAt` ties on `_id` so those pages are stable: migration 017 stamps every seeded rule with one shared timestamp, and without the tiebreaker two pages drawn from two orderings could overlap or skip a rule. The audience tool likewise carries the Analytics tab's site-wide Accounts card in its own `accounts` block, scoped `site-wide, not windowed` and `null` (never `0`) when identity is unavailable — including `walletAdoptionRate`, which stays null when the `'wallets'` service is absent even though `'accounts'` resolved, since a `0` there is indistinguishable from a measured zero-adoption site. So a non-windowed total cannot be folded into the windowed funnel beside it, and missing data cannot be narrated as a figure.

**Attribution is stated per response, not just per description.** The breakdown tool stamps each result with `attribution`: `session-scoped` for sources and landing pages, `first-touch` for campaigns, `in-window` for geo and devices. A single sentence in a description is easy for a model to lose by the time it narrates a number, and this is the field most likely to be narrated backwards — the description previously claimed all three were first-touch, which had been true before the sources and landing-pages reads moved to session scope and was then the exact opposite of what the dashboard tooltip said over the same figures.

**Narrowing to one country.** The overview, breakdown, audience, and new-visitor tools take an optional `country` (ISO-3166 alpha-2, normalized to uppercase, anything else rejected). The Cloudflare sentinels `XX` and `T1` are rejected too, through the same `isStorableCountryCode` test ingestion applies, because no stored row ever carries them and a query for either could only report an empty country as a real zero. It travels on `IAnalyticsDateRange.country`, and `rangeParams` and `sessionRangeParams` apply it as a bound `country = {country:String}` filter, so every read built on them narrows without a per-read change, including the membership subquery and the overview's previous comparison window. The filter is per event row: a visitor seen from two countries counts in each, and a session is built from that country's rows only. New-visitor rows still report each visitor's true first touch, because the outer first-touch grouping reads full history; only which visitors qualify is narrowed. Three things are deliberately not scoped. The overview's live counter has no window, so the tool returns `liveVisitors: null` when a country is set rather than pair an all-country figure with Korean ones. The audience tool's `accounts` block stays site-wide. And `country` with dimension `geo` is rejected, since the answer would only repeat the filter. The REST routes and the dashboard do not expose the filter yet.

**Why six tools declare `surfacesUntrustedContent`.** Anything a visitor can put on the wire and later read back is an injection vector. Unclassified User-Agents, GSC search queries, new-visitor `searchKeyword`/`utm`, and the per-event tool's `userAgent`, `path`, and `referrerDomain` are the obvious cases, but three more are easy to miss: every `getOverviewTrend` bucket carries `topPaths`/`topSources`/`topCountries`, the breakdown tool returns `utm_*` (campaigns) and `path` (landing pages, source drill-down) verbatim, and the crawler tool's `top-paths` view is a raw `path` aggregate. All arrive on the **public unauthenticated** ingestion endpoints, where `clampUtm` and `sanitizePath` apply length caps and a leading-slash rule but never an allow-list — so a crafted path or campaign is storable and surfaces once it ranks in a bucket. Only `tronrelic-get-audience-behavior` (cohort counts plus identity's account totals — every value a number this module or identity computed) and `tronrelic-get-redirect-analytics` (rules authored by an admin, and beaconed patterns validated against the enabled rule set at ingestion) are genuinely clean. The declaration is what makes the governor wrap and screen the result; omitting it means no wrap at all. Adding these arms the untrusted-content leg of the lethal-trifecta detector — check the banner and screen posture at `/system/ai-tools` after enabling them alongside any egress tool.

**What is deliberately absent, and the one exception.** `getVisitors` and `getPageHits` — one person's browsing history, pseudonymous by tid but re-identifiable once a tid carries a `user_id`, and now carrying `ipHash`/`userAgent` as well — are exposed to no tool, and `getHighVolumeSubnets` is excluded because a subnet hash is a source-correlation key. `getNewVisitors` ships only through `projectVisitorOrigin`, which strips `userId` and `subnetHash` so rows carry acquisition shape with no correlation key. Re-adding any of these is a privacy decision, not a convenience one.

The per-event tool is that decision, made once and on purpose: diagnosing automated traffic needs exactly the correlation keys the other tools strip, so it returns `ipHash`, `subnetHash`, and `tid`. It is declared `secret` instead, which keeps it below the [MCP](../mcp/README.md) safety floor. It can never be granted to the general `mcp-users` group, only to a narrower group an admin has cleared for restricted tools on `/system/mcp`. The governor also redacts its arguments in the audit record, and the lethal-trifecta detector counts it as private data. Because it also surfaces untrusted content, this one tool supplies two of the three legs, and enabling it beside any egress tool completes the trifecta reported at `/system/ai-tools`. It still never returns an account id. The Visitors tab itself, keyed per visitor with acquisition history, remains unanswerable by an agent.

The **AI tab** on `/system/traffic` lists these tools with their capability badges, description prompt, and input examples, and toggles each one. It proxies the core registry through `GET /api/admin/users/analytics/ai-tools` and `PATCH /api/admin/users/analytics/ai-tools/:name` (both `requireAdmin`), filtered to this provider — a name owned by another provider 404s. Enabled state lives in core, so a toggle here is the same switch the `/system/ai-tools` Registry tab flips.

**Funnel composition is shared, not duplicated.** `composeConversionFunnel` (exported from `services/traffic.service.ts`) joins the ClickHouse binary funnel to the acquisition stage resolved against Better Auth `createdAt`. Both `GET /analytics/conversion-funnel` and the audience tool call it, so the REST panel and the AI answer cannot drift into reporting different funnels for one window. When identity is unavailable the stage reads 0 rather than failing the funnel — indistinguishable from a genuine zero, which is why the tool description tells the model to say "0 or unavailable". Note the cost profile: `getActiveAccountIds` is uncapped and the helper fans out one directory read per active account, batched `ACCOUNT_LOOKUP_BATCH_SIZE` wide. A model calling this repeatedly at `30d` — now `90d` too, since the tools carry the dashboard's full preset list — is a heavier load than the one operator-triggered dashboard panel it was written for, which is why the tool description names the cost and tells the model to call it once per question rather than per follow-up.

See [system-ai-tools.md](../../../../docs/system/system-ai-tools.md) for the tool contract, capability vocabulary, and the accountability every tool must meet.

## Lifecycle

**`init()`** runs `initGeoIP()`, then constructs `GscService` (creates indexes) and `TrafficService` (no-ops without ClickHouse), then `IgnoredUsersService` (creates indexes) and seeds `TrafficService`'s ignore cache from it so the exclusion is live from the first read, wraps that cache in `TrafficIgnoreList`, then builds the traffic + bootstrap controllers. **`run()`** registers the `Traffic` menu item under the System container, mounts the traffic, analytics, and bootstrap routers — the `/api/admin/users/*` routers ahead of the identity module's accounts `/api/admin/users` catch-all — publishes `'traffic-ignore-list'`, registers the daily `gsc:fetch` job, and starts the `'ai-tools'` registry watch that registers the read-only analytics tools.
