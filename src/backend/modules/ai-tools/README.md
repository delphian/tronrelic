# AI Tools Module

Provider-agnostic governance for AI tools — the registry every tool registers with, and the governor every AI provider plugin executes through. Owns capability classification, policy (rate / approval / autonomous default-deny), the invocation audit trail, and the human-approval queue.

## Why This Module Exists

The AI *provider* is a swappable plugin (`trp-ai-assistant` for Anthropic today; OpenAI/Google could follow). If tool registration and governance lived in the provider, swapping providers would lose them. This module makes core the owner: tools register with `'ai-tools'`, every call runs through `'ai-tool-governor'`, and a provider swap loses nothing about tool governance. It is a module, not a plugin, because the platform's accountability contract cannot be optional.

## The Governed Pipeline

`governor.invoke(name, input, ctx)` runs, in order: resolve the tool → enabled-check → per-query allowlist check (deny when `ctx.toolAllowlist` is present and omits the name — narrows only, never widens; a `hosted:` entry in that list is inert here, since it can never match a registry name and a hosted tool never reaches the governor) → validate `input` against the tool's schema → `ai.toolInvoke` seam (a handler throws `HookAbortError` to veto or hold) → policy check → execute the handler under a 30s wall-clock budget → `ai.toolResult` seam (a waterfall handler alters the raw result or throws `HookAbortError` to withhold it) → wrap the result for provenance → write an `IToolInvocationRecord` → `ai.toolInvoked` seam. It fails safe: an internal fault denies rather than running an ungoverned handler, and a handler fault is caught, audited, and returned to the model as a reason. The result is `{ status: 'ok' | 'denied' | 'pending-approval' | 'error', content, error?, recordId }`.

**Provenance wrap:** when the tool declares `surfacesUntrustedContent`, a successful result's `content` is the `{ untrustedContentNotice, data }` envelope from `wrapUntrustedToolResult` (`@delphian/tronrelic-types`) — the attacker-influenceable payload labeled as data so the provider forwards it JSON-escaped, never as raw text the model could read as instructions. The audit `resultDigest` records the raw value; only what the model sees is wrapped. Because this lives in the governor, no provider transport can bypass it.

**Untrusted-content screen (active):** the wrap is passive; on top of it the governor runs an optional screen on a `surfacesUntrustedContent` result before forwarding. The screen is skipped on the `mcp` trigger path whatever the config says: each screen is a paid model call, and an MCP user's client controls how often it calls. The provenance wrap still applies there. Per `ScreenConfigService`, when enabled (and, under `trifecta` posture, only when `isEgressReachable()` reports an open egress) it calls the active provider's `screenUntrustedContent(text)` — the provider's cheapest model, in an isolated tool-less call — and **withholds** a flagged result from the model (`{ contentWithheld: true, reason }`), recording the verdict on `IToolInvocationRecord.screen` and an offender hit via `policy.recordScreenHit()`. When the installed provider offers **no** screen at all, the configured `onFailure` decides: `open` forwards the wrapped result, `closed` withholds. A screen that **ran and failed** — threw, or returned a malformed verdict — always withholds, whatever `onFailure` says. The two are different conditions: the second made the call against this exact payload and got no verdict back, and the reasons it fails track the payload being dangerous (a result too large for the screening model's own context window, or one crafted to break the call), so forwarding would single out the one result nobody could vet. A flagged-offender tool is throttled by `ToolPolicyEngine` once it crosses `offenderThreshold`. The model choice is the provider's; whether/when to screen is core config.

## The `mcp` Trigger Path

The [MCP module](../mcp/README.md) calls the governor for tools that a non-admin member of `mcp-users` invokes from their own AI client. Those calls carry `triggerPath: 'mcp'`, `actor.kind: 'user'`, the user as `endUser`, and an `origin` (`clientId`, `credentialId`, `ip`) that the audit record copies. The path adds these rules:

| Rule | Where |
|---|---|
| A missing `toolAllowlist` is denied (it would otherwise mean "every enabled tool") | Governor, after the allowlist check |
| A missing end user is denied | Policy engine, first gate |
| The tool must pass `getMcpToolIneligibility` (declared, read-only, reversible, not `secret`, not paid), unless its name is in both `ctx.mcpRestrictedTools` and `ctx.toolAllowlist` — which the MCP endpoint sets only for tools it served through a user group an admin cleared for restricted tools | Policy engine, first gate |
| A tool whose effective policy requires approval is denied rather than parked | Policy engine, first gate |
| Per-user windows of 30 calls per tool and 60 calls overall per minute, charged before the shared windows; a call over the user's own budget never ticks the shared counters | Policy engine `consumeRate` |
| The untrusted-content screen is skipped; the wrap is kept | Governor `screenUntrusted` |
| Curation auto-approve never applies (it is `interactive`-only), and the external-tool default-deny does (it keys on `!== 'interactive'`) | Existing policy, unchanged |

## System Log Surface

What the module writes to `system_logs`, queryable at `/system/logs`. The audit collection stays the record of *what happened*; these lines are the triage view over it, so none of them carries tool arguments — `recordId` is the handle for pulling the full, sensitivity-redacted record instead. Every line is a child of the module logger, so each carries `module: 'ai-tools'` in its context. All are gated by the configured log level like any other log; set the level to `warn` to keep only the rows that need attention.

| Level | Message | Fires when | Key context |
|---|---|---|---|
| info | `AI tool ran: <name>` | Any invocation that reached the handler and did not error | `tool`, `triggerPath`, `status`, `durationMs`, `sideEffect`, `sensitivity`, `screenFlagged`, `queryId`, `recordId` |
| info | `AI provider-hosted tool ran: <name>` | A vendor-hosted tool (Anthropic `web_search` / `web_fetch`) reported after the fact through `recordServerToolInvocation` | `hosted: true`, `tool`, `triggerPath`, `status`, `sideEffect`, `sensitivity`, `queryId`, `error`, `recordId`. No `durationMs` or `screenFlagged` — the provider reports neither, and a defaulted `0ms` would read as a real measurement |
| warn | `AI tool denied: <name>` / `AI tool error: <name>` | Refused before execution — unregistered, disabled, outside the query allowlist, schema-invalid, hook-vetoed, or policy-denied | `reason`, `triggerPath`, `sideEffect`, `recordId` |
| warn | `AI tool held for admin approval: <name>` | An external/irreversible call parked in the approval queue | `approvalId`, `reversible`, `recordId` |
| error | `AI tool handler failed: <name>` | The handler threw or exceeded its timeout | `error` |
| warn | Untrusted-content screen lines | The screen flagged a result, could not run, or failed open/closed | `tool`, `reason`, `why` |
| info | `Saved prompt run completed` | An autonomous run (cron, hook, or run-now) ended with a real answer | `promptId`, `name`, `triggerId`, `outcome: 'answered'`, `stopReason`, `model`, `durationMs`, `responseChars`, `toolCalls`, `inputTokens`, `outputTokens`, `costUsd` |
| warn | `Saved prompt run produced no usable answer: <reason>` | An autonomous run returned but did not answer — truncated, out of tool rounds, paused, refused, or empty | The same context plus `detail`, and an `outcome` naming which of the five it was |
| error | `Saved prompt execution failed` | The query itself threw | `err`, `promptId`, `name`, `triggerId` |
| error | `Streaming AI query failed before completing` / `AI query failed` | An interactive Query-tab run threw. The browser gets a fixed sanitized sentence or a 502, so this is the only statement of the real cause | `err`, `queryId` (streaming only), `model`, `conversationId` |
| warn | `Failed to compose injected system prompt for interactive query; proceeding without it` | A `{%name%}` in a system prompt would not resolve. The query still runs, but the master and audience-scoped prompts silently stop applying — the scheduled runner logs the same condition | `err`, `userId` |
| error | `AI tool governance threw instead of denying; the invocation left no audit record` | The governor pipeline broke its own never-throws property. No audit row exists for that call | `err`, `tool`, `queryId`, `triggerPath` |
| error | `Prompt variable operation failed: <what>` | A variable create/edit/delete/classify failed for a reason that is not caller-actionable (the 500 branch; a 400/404/409 is not logged) | `err`, `fallback` |
| warn | `Prompt variable "<name>" failed to resolve while sizing` | A resolver threw while the Registry tab measured it. The row shows 0 bytes, which reads as empty rather than broken, and the next prompt referencing it will fail too | `err`, `variable` |

Every autonomous run closes with exactly one of the three saved-prompt lines. That matters because the run previously logged `Running saved prompt` on the way in and nothing at all on the way out unless the query threw, so a prompt that finished without producing anything was indistinguishable in the logs from one that worked. Filtering `/system/logs` to `warn` surfaces exactly the runs that need attention.

**A rejected input is not logged; a fault is.** The admin routes answer a bad request with a 400, 404, or 409 whose body already states what was wrong, and logging those would fill the log with other people's typos. Every line above marks something the caller was *not* told — a sanitized browser message, a bare 500, a silent degradation, or a broken invariant.

The two error paths are distinct and each logs once. A handler that throws or times out produces the `error` line carrying the cause, and the completion line deliberately skips that status rather than reporting the same call twice. An error *before* execution — a governance hook itself failing, or a tool unregistered between approval and release — never reached a handler, so it produces the `warn` refusal line with its reason instead.

## Capability Classification & Default State

A tool declares `IAiToolCapability`; the registry sets its first-boot enabled state from it. **Least privilege:** `external`, irreversible, or money-spending tools ship **disabled** (opt-in); everything else ships enabled. A persisted admin toggle always overrides.

| Class signal | Default | Policy consequence |
|---|---|---|
| `sideEffect: 'read'` | enabled | light rate cap |
| `sideEffect: 'write'` | enabled | rate cap + full-arg audit |
| `sideEffect: 'external'` / `reversible: false` / `spendsMoney` | **disabled** | rate cap + approval (irreversible & not self-curated) + **autonomous default-deny** (unless self-curated) |
| `sensitivity: 'secret'` | — | arguments redacted in the audit record |
| `operatesOnUserOwnedObjects` | — | **denied unless `ctx.endUser` is present** — a user-scoped tool cannot run under ambient authority |

**Autonomous default-deny:** on `triggerPath` `scheduled` or `programmatic`, an `external` tool is denied unless it declares `forcesCuratorReview: true` — its own human-review queue makes an unattended call safe, because the call can only draft into that queue — or an admin policy override grants `allowUnattended`. **Approval:** an external/irreversible tool that does not self-curate parks as `pending-approval` and runs only when an admin approves; a `forcesCuratorReview` tool relies on its own queue, so the governor adds no second gate. Both gates derive from the capability — a tool cannot opt itself out of either; only an admin policy override (`IToolPolicy`) can relax them.

**Object-authorization precondition:** a tool that declares `operatesOnUserOwnedObjects: true` is denied — first, before any other check — when the invocation context carries no `endUser` principal (or its `userId` is blank). Such a tool must scope every object access to that end user; running it under the actor's ambient server/admin authority is the confused-deputy (BOLA) failure, since there is no principal to authorize against. When the gate passes, the governor hands the handler the trusted principal as its second argument (`handler(input, principal)`, never from model `input`), so the tool can authorize against `principal.userId`. The actor's `kind` does not satisfy the gate — an admin is ambient authority, not a specific end user. Core cannot verify the handler performs the ownership check, but it refuses to run the tool without the identity the check needs, turning "execute in the user's context" from honour-system into an enforced precondition. The MCP endpoint is the first non-admin path to supply a principal (its calls always carry the signed-in user as `endUser`), so the gate is live there; no tool declares the flag yet. See [system-ai-tools.md](../../../docs/system/system-ai-tools.md).

**Curation mode:** a curation-capable tool (`forcesCuratorReview` honored) defaults to `IToolPolicy.curation: 'require'` — every held effect waits for a human in the curation queue (`/system/curation`). An admin may override to `'auto-approve'`: an explicit, audited bypass that releases that tool's held effects without manual review. It is honored **only on the interactive trigger path**; a `scheduled`/`programmatic` run ignores it and falls back to a manual hold, so an unattended run can never auto-execute an external effect. Auto-approve un-gates the egress, so the tool re-arms the lethal-trifecta signal (`exfiltrationGated` → `exfiltrationOpen`). The governor carries the decision across the handler call via the curation module's `runWithCurationAutoApprove` `AsyncLocalStorage`, and `CurationService.hold()` approves the new item under `system:policy-auto-approve` — a distinct, non-human decider in the audit.

**Lethal-trifecta detection:** `detectTrifecta()` scans the *enabled* set for the co-presence of a private-data source, a `surfacesUntrustedContent` source, and an `external` sink — the combination that lets injected text read a secret and exfiltrate it in one turn. The private-data leg counts both a `sensitivity: 'secret'` reader tool and a `secret`-classified prompt variable (passed in from `PromptVariableRegistry.getSecretVariableNames()`), surfaced in `ITrifectaStatus.privateDataVariables` — a secret variable splices secret content into the prompt with no tool call, so it forms the leg on its own. The exfiltration leg splits by whether the channel is autonomously closable: a curator-gated sink (`forcesCuratorReview` honored and not auto-approved) is *supervised*, not lethal — per the Rule of Two, a human releasing every effect is the sanctioned escape hatch. `GET /trifecta` returns `severity` (`safe` / `supervised` / `lethal`), the `present` boolean (= `lethal`, back-compat), and the tool names per leg with the egress split into `exfiltrationOpen` / `exfiltrationGated`. An operator breaks the chain by disabling a leg; an admin auto-approve bypass moves a sink from gated to open, re-arming `lethal`. `POST /trifecta/preview` runs the same detector scoped to a hypothetical `toolAllowlist` — both halves filtered to the selection (governed registry tools by their plain name, provider-hosted tools behind the `hosted:` prefix), with secret variables still folded in, since a variable injects into the prompt whichever tools a run selects — so the saved-prompt editor's per-run badge shows a narrowed selection break the chain live, including when the narrowing is unticking web search. The preview also takes the prompt's pinned `providerId` and `model`, because the hosted-tool switches are stored per model and a badge resolved from the active provider's configured model would omit a tool the pinned run really grants — reporting a lethal run as safe.

## Service Contracts

### `'ai-tools'` → `IAiToolRegistry`

Tool providers consume this. `registerTool(tool, providerId)`, `unregisterTool(name)`, `getEnabledToolDeclarations()` (handler-free, for a provider to format), `getTool`, `listTools`, `listToolInfo`, `setEnabled(name, enabled)`.

`registerTool` lints the capability declaration first (`lintToolCapability`, `services/capability-linter.ts`). A self-contradictory or invalid declaration is an `error` and **rejects the registration** — an unrecognised `sideEffect`/`sensitivity` value (a typo would otherwise slip the default-deny or skip audit redaction, both of which match on exact strings), a `curationTypeId` without `forcesCuratorReview` (the binding it is supposed to verify), or a `spendsMoney` tool with no valid positive `costPerCallUsd` (the cost ceiling cannot meter a paid tool whose per-call cost is missing, non-finite, zero, or negative — a $0 charge never trips the ceiling — so it fails closed rather than registering unmetered). Likely misclassifications are `warn`s that log and still register: a `read` tool marked irreversible or money-spending, or — the F3 footgun — a description that reads like an untrusted-content source (memo, tweet, timeline, fetched page) without `surfacesUntrustedContent` set. Core cannot read a handler's intent, so the untrusted-content check is a heuristic nudge, not a reject; over-declaring only makes the trifecta banner more cautious. The linter is pure and unit-tested independently of the registry.

### `'ai-tool-governor'` → `IAiToolGovernor`

The AI provider plugin consumes this. `invoke(name, input, ctx)` returns `IToolInvocationResult`. The concrete `AiToolGovernor` also exposes `approve(approvalId, by)` / `reject(approvalId, by)` for the admin surface, and `setBroadcast(fn)` which the module wires to `WebSocketService` so governed events emit refetch signals.

### `'ai-providers'` → `IAiProviderRegistry`

The installed AI provider plugin registers itself here, handing the registry both its metadata and its **executable `IAiProvider` instance**: `registerProvider(info, instance)` / `unregisterProvider(id)` / `listProviders()` / `getActive()`. `listProviders()` backs the provider-agnostic Provider panel; `getActive()` returns the active provider's executable instance (or `null`) and is the provider-neutral way for core surfaces (the query backend) and consumer plugins to actuate AI — there is no vendor service key. `trp-ai-assistant` registers on enable and unregisters on disable.

### Consumes `'curation'` → `ICurationService`

Curation is **not** owned here — it lives in its own [curation module](../curation/README.md) and publishes `'curation'`. This module consumes it: the module `watch`es the registry and, while `'curation'` is present, injects `ToolPolicyEngine.setCurationResolver((typeId) => curation.hasType(typeId))` so the governor verifies a tool's `curationTypeId` binding live — relaxing the tool's gates only while its owning type is registered, and re-tightening (deny-all) the moment curation unregisters. The same `onAvailable` also **registers** the module's own `core:social-post` curation type, so the built-in `propose-social-post` tool's binding resolves against a live type. The governor also imports `runWithCurationAutoApprove` from the curation module to wrap a governed handler call for the interactive auto-approve bypass. Full design: [system-curation.md](../../../../docs/system/system-curation.md).

### `'prompt-variables'` → `IPromptVariableRegistry`

The single registry of prompt variables — the `{%name%}` tokens an AI provider expands into a prompt. Holds two kinds behind one service (the Menu module's dual-backing pattern): `dynamic` variables a provider plugin or core module registers in code (`registerVariable`, classify-only) and `static` variables an admin authors and persists (`createStatic`/`updateStatic`/`deleteStatic`, full CRUD). The AI provider consumes `expandAll`/`expandWithMetadata` at request-build time, so a prompt expands admin-authored statics alongside built-ins. `classify()` sets a variable's sensitivity — a static stores it on the document, a dynamic persists an admin override over its code-declared default. `getSecretVariableNames()` feeds the trifecta detector. A new static defaults to `secret` (fail-safe), and a static that shadows a registered dynamic name is rejected. This module registers a core-owned set of **built-in dynamic variables** (`variables/`) at init; the installed AI provider and other plugins register their own the same way through the service watch. The module owns the registry — it and the built-in set were lifted out of the `trp-ai-assistant` plugin.

| Category | Built-in dynamic variables |
|---|---|
| Blockchain & Network | `system-status`, `chain-params`, `tx-activity`, `tx-types`, `tx-week` |
| System Health | `observer-stats`, `log-summary`, `server-info` |
| Site & Content | `site-info` |
| Database Access | `cache-keys` |
| Time & Scheduling | `run-window-24` |

`listSummaries()` returns each variable's name, pattern, description, category, kind, and effective sensitivity without resolving anything and without a static's `content`. Use it instead of `listInfo()` whenever the caller only needs to know what exists, because `listInfo()` runs every dynamic resolver to measure its size.

### Prompt-Variable Tools

Two built-in AI tools read the registry. Both are `read` / reversible / `internal`, ship enabled, and appear on the Registry tab under the `ai-tools` provider group.

| Tool | Input | Returns |
|---|---|---|
| `ai-list-prompt-variables` | none | `total`, `returned`, `truncated` (more than 500), and `variables[]` of the `listSummaries()` fields plus `readable` (false for `secret`) |
| `ai-get-prompt-variables` | `names`: 1–10 names, with or without `{% %}`; `offset`: optional character position to start each value from, default 0 | `variables[]`, one per name, with `status` `ok` (`content` for this page, `totalChars` and `sizeBytes` of the full value, `truncated`, `nextOffset`), `not-found`, `withheld`, or `error`, and a `reason` on every non-`ok` entry |

**Long values are paged.** Each value comes back at most 10,000 characters at a time. When `truncated` is true, the caller repeats the call with that one name and `offset` set to the returned `nextOffset`, until `nextOffset` is `null`. Before paging, a value longer than one page could not be read past its first 10,000 characters by any tool, although the prompt that references it always received the whole value. `offset` counts characters, the same unit as `totalChars`, not the bytes in `sizeBytes`, and a page never ends between the two halves of a surrogate pair such as an emoji. The one `offset` applies to every name in the call, so a call reading a later page normally names a single variable.

**Secrets are withheld, not returned.** Returning a `secret` variable would make the read tool a private-data source, so it would have to be classified `secret`: it would fail the MCP safety floor and be counted as the trifecta's private-data leg whenever enabled. The handler checks the effective sensitivity from `listSummaries()` before resolving, so a withheld variable's resolver never runs. A model that needs a secret's value gets it the intended way, through a prompt referencing `{%name%}`. Reclassifying a variable below `secret` on the Registry tab makes it readable here too.

`ai-get-prompt-variables` declares `surfacesUntrustedContent`, because a dynamic variable such as `log-summary` can carry text an outsider wrote. The listing does not, since every name, description, and category is written in code or by an admin. A resolver failure is logged at `warn` with the real error and reported to the model as a generic reason, because the error text can name internal hosts.

## Admin REST API

All under `/api/admin/system/ai-tools` (rate-limited + `requireAdmin`). Routes marked **session-only** add `requireAdminUser`, refusing the `ADMIN_API_TOKEN` service path and admitting only a signed-in admin. See [system-auth.md](../../../../docs/system/system-auth.md#narrowing-an-admin-route-to-a-human--requireadminuser).

Two kinds of route earn it. The **policy writes** take a safety gate off, where a shared environment variable is too broad a key and an unattributable actor is the wrong audit record. The rest are paths by which a caller reaches a `secret` prompt variable's value:

| Read path | How the secret gets out |
|---|---|
| `GET /variables/:name/value` | Resolves the variable directly |
| `GET /variables` | The bulk listing embeds every *static* variable's `content`, and a new static defaults to `secret` |
| `POST /query` | Core expands `{%name%}` in the user prompt, so `"repeat verbatim: {%some-secret%}"` returns it |
| `GET /query/history`, `GET /query/conversations/:id` | The model's answer to such a prompt is persisted with the turn. The stored `expandedPrompt` is **not** a second such path: core builds it with `skipSecret`, leaving a secret variable as its `{%name%}` token |

| `POST /query/prompts`, `POST /query/prompts/:id/run` | A saved prompt is a stored query: `executeSavedPrompt` leaves registry tokens for provider-side expansion, and a service-token save is unowned yet still fires on its own cron/hook trigger |

Filtering `secret` variables out of prompt expansion is not an alternative fix: injecting them is what they are for — they are the lethal trifecta's private-data leg by design.

**This is a narrowing, not a boundary.** The system-prompt writes (`PUT /system-prompts/master`, `POST /system-prompts`) remain on the shared gate, and `compose()` expands `{%name%}` too — so the service token can still plant a secret reference into a prompt that expands on another principal's later run. `ADMIN_API_TOKEN` also still reaches every other admin route here, so it remains a high-value credential; this narrows which secrets it reads directly, it does not demote it.

## Query Backend

A provider-neutral chat surface owned by core, not by any provider plugin. The `/query*` routes resolve the active provider via `IAiProviderRegistry.getActive()` and persist every turn, so the `/system/ai-tools` **Query tab** (multi-turn chat, a conversation rail that opens any past thread in place, model picker, streaming + non-streaming) survives a provider swap. There is no batch mode here — batch stays a provider concern.

The tab's frame follows current chat interfaces. The chat pane fills the viewport below the page chrome, so the transcript is the one scrolling region and the composer stays pinned to the bottom of the screen; the transcript follows a streaming answer only while the reader is at the live edge and offers a "Latest" button back; a send anchors the new message at the top of the pane; Enter sends and Shift+Enter inserts a newline; per-message actions appear on hover. The tab stays mounted while the dashboard's other tabs are open and writes the open conversation to `?conversation=`, so neither a tab switch nor a refresh loses a thread.

Streaming is fire-and-forget: `POST /query` (default) requires a client-generated `queryId` and the caller's live `socketId`, fires `provider.queryStream(opts, onChunk)`, returns 200 immediately, and appends an `IAiQueryRecord` when the stream settles. Each chunk reaches the browser as an `ai-tools:query-stream` event carrying an `IAiStreamChunk` (with `queryId`), emitted to that one socket via `WebSocketService.emitToSocket` — never broadcast, because a chunk carries answer text, tool arguments, and tool results.

Because `socketId` arrives in the request body, the route proves it before writing to it: `WebSocketService.getSocketUserId(socketId)` must return the calling admin's own user id, else `403`. Without that check `requireAdmin` alone would let one operator stream their transcript into another person's browser. The corollary is that only the Better Auth session path can stream — a service-token call has no user identity to match a socket against, so it is told to use `stream: false`. The check runs before the `QueryStreamRegistry` sink is registered, so a refusal leaves the `queryId` unclaimed for a retry. Note that ownership is read from the session resolved at the socket's *handshake*: a browser whose socket connected before sign-in reads as anonymous and must reload before it can stream. Non-streaming (`stream: false`) awaits `provider.query` and returns the result inline. Both interactive paths record history with persisted `mode` `'stream'` or `'programmatic'`; the cron runner writes the third `AiQueryMode` value, `'scheduled'` (see [Saved Prompts & Scheduling](#saved-prompts--scheduling)). All three share one builder, `buildAiQueryRecord`, so the record shape never drifts between paths.

**A returned result is not a successful run.** A provider returns an ordinary `IAiQueryResult` for a run that exhausted its output token budget, used up every agentic tool round, paused mid-turn, was declined on safety grounds, or produced no text at all, so recording `status: 'completed'` whenever a result came back made all five look identical to a run that answered. `classifyAiQueryOutcome` (`services/classify-query-outcome.ts`) draws the distinction from the vendor-neutral `stopReason` and the answer text, and `buildAiQueryRecord` calls it, so every path — stream, programmatic, scheduled, hook-fired, run-now — reaches the same verdict for the same run. The record carries `outcome` (`answered` · `truncated` · `tool-limit` · `paused` · `refused` · `empty` · `failed`), the provider's `stopReason`, a `status` of `completed`/`incomplete`/`failed` derived from the outcome, and an `errorMessage` that now holds the incompleteness reason as well as a thrown error. The Query tab badges an incomplete run in a warning tone naming the outcome. Records written before these fields exist carry neither `outcome` nor `stopReason` and never carry `incomplete`, so an old row that would classify as incomplete today still reads `completed`.

**The record stores both the template and its expansion.** `prompt` is the text exactly as typed or saved, `{%name%}` tokens intact, because that is the reusable template a bookmark has to capture. `expandedPrompt` is the same text with its variables resolved, which is what the run was actually asked. History displays the expansion and the Query tab keeps the template on the turn, so a reopened conversation shows real data while "save this turn as a prompt" still writes something reusable. Re-expanding at read time would be wrong: a prompt variable reads live data, so an old record would answer with today's values instead of the ones the run saw. `expandedPrompt` is dropped when expansion changed nothing, and is absent on records written before the field existed — readers fall back to `prompt`. The terminal `done` stream chunk carries the same string, so a live transcript reads identically to a reopened one, and the next turn replays that exact text as prior context rather than a template that would re-resolve against newer data.

**The record also stores the run's `toolAllowlist`**, in the same three states the run used — `null` for unrestricted, `[]` for none, a list for that subset, with a provider-hosted tool behind the `hosted:` prefix. Nothing else preserves it: a transcript shows only the tools the model chose to call, which is a subset of the grant. Reopening a conversation reads the **opening** turn's model and allowlist back into the composer, so the message bar continues the thread on the terms it ran under; the opening turn rather than the latest, because an interactive grant is one-shot and clears after each send, so a later turn usually recorded an empty one. The field is absent on records written before it existed, and a reader must not read that absence as `null` — it means unknown, and the Query tab leaves the composer alone rather than inventing a grant. The two `IAiQueryRecordContext` fields (`expandedPrompt`, `toolAllowlist`) are grouped into one trailing argument on `buildAiQueryRecord` because they describe the *request*, where every positional parameter before them describes the outcome.

Core resolves the variables for the record in `AiToolsController.query` and in `executeSavedPrompt`; **the provider still receives the raw prompt and still runs its own expansion.** Handing the provider pre-expanded text would mean its pass re-scans a string that now contains variable *data*, so a `{%name%}` arriving inside a TRON memo or a log line would resolve — turning attacker-controlled content into a secret-variable read, which is exactly the lethal-trifecta path this module exists to watch. Suppressing that pass with `IAiQueryOptions.expandVariables: false` is not the alternative either, because the installed provider applies that flag to its own configured system prompt as well, so every core query would lose the variables an operator put there. The price of keeping both passes is that a variable resolves twice per query. That is a cost on an admin surface rather than a correctness problem, but it is worth knowing before adding an expensive resolver.

**Core's pass runs with `skipSecret`, the provider's does not.** `IPromptExpansionOptions.skipSecret` leaves every `secret`-classified variable as its literal `{%name%}` token instead of resolving it, and core sets it on both record-building call sites. The model is unaffected: the provider's own pass resolves everything, and splicing private data into the request is what a secret variable is for. The distinction is between a copy that is *sent* and a copy that is *kept* — `module_ai-tools_query_history` has no retention sweep, so a stored value lives indefinitely, and `/system/database` serves that collection under plain `requireAdmin`, which admits the shared service token the history routes above deliberately refuse. Under `skipSecret` the variable is never resolved at all rather than resolved and masked, so no copy of the value exists in that call for a later change to leak. The token that survives in its place tells a reader exactly where a secret went.

Because a `dynamic` variable defaults to `internal` and only an admin-authored `static` defaults to `secret`, this costs a default deployment nothing — every built-in variable still expands into the record. An operator who wants one particular variable's value recorded reclassifies it below `secret` through `PUT /variables/:name/classification`, which is per-variable, audited, and the same control the trifecta detector reads, rather than a global switch that would turn the protection off wholesale. This closes the deterministic path only: a prompt that asks the model to repeat a secret back still lands it in `responseText`.

History lives in `module_ai-tools_query_history` (`IAiQueryRecord`), indexed unique `{ id }`, descending `{ createdAt }`, sparse `{ conversationId, createdAt }` for oldest-first thread reads, and sparse `{ savedPromptId, createdAt }` for one saved prompt's runs newest first. Turns sharing a `conversationId` form one chat.

**A saved-prompt run names its prompt.** `executeSavedPrompt` passes `savedPromptId`, and `triggerId` when a trigger fired the run, to `buildAiQueryRecord` on every branch that writes a row: a completed run, a failed run, and a run skipped before the query because no provider or owner resolved. A manual run-now records the prompt id alone. Before these fields, nothing in a run record pointed back to its prompt, because each autonomous run gets a fresh `conversationId` and the prompt text stops matching once the prompt is edited. Interactive runs carry neither field, and the builder leaves them out rather than storing them empty. Runs recorded before the fields existed carry neither, so a prompt's history in the tools below starts from the deployment that added them. Each record may carry an ordered `transcript` (`IAiTranscriptSegment[]`) — thinking, answer text, tool calls, and tool results in occurrence order — so a reopened turn replays its full structure, not just `responseText`. `buildAiQueryRecord` writes it whenever the provider returns one (thinking only under `persistThinking`); the Query tab falls back to `responseText` when it is absent.

### Prompt-Run Tools

Three built-in AI tools read the query history. All are reads, ship enabled, and sit in the `ai-tools` group on the Registry tab.

| Tool | Class | Input | Returns |
|---|---|---|---|
| `ai-list-prompt-runs` | `internal` | Optional filters `savedPromptId`, `mode`, `status`, `outcome`, `since`, `until`; `limit` (default 25, at most 100), `offset` | `total` (matching the filters), `offset`, `limit`, `returned`, `nextOffset` (`null` on the last page), and `runs[]` newest first: metadata (`id`, `conversationId`, `mode`, `model`, `status`, `outcome`, `stopReason`, timestamps, `costUsd`, `usage`, `savedPromptId`, `triggerId`), a 200-character `promptPreview` of the template, `promptChars`, `toolCalls`, `hasTranscript` |
| `ai-summarize-prompt-runs` | `internal` | The same optional filters | `filters` as applied, `runs`, `byStatus`, `byOutcome` (runs with no recorded outcome counted as `unrecorded`), `costUsd`, `pricedRuns`, `averageCostUsd` (`null` when nothing was priced), `inputTokens`, `outputTokens`, `firstRunAt`, `lastRunAt`, `lastAnsweredAt`, `lastAnsweredRunId` |
| `ai-get-prompt-run` | `secret`, surfaces untrusted content | `id`: a run id (that one turn) or a conversation id (every turn, oldest first, at most 50); `start`: the previous page's `next`, default 0 | `found`, `matchedBy` (`run` or `conversation`), `start`, `next` (`null` on the last page), `turnsTruncated`, `truncatedFields`, and `turns[]` with metadata, `toolAllowlist` plus `toolAllowlistKnown`, `continued`, `prompt`, `expandedPrompt`, `errorMessage`, and `cutFields` (left out when `continued`), then `segmentStart`, `segmentCount`, and this page's `transcript` segments |

**The listing and the summary share one filter**, read by the same code and turned into the same database filter by `AiQueryHistoryService`, so a count from the summary always matches the `total` the listing reports for the same arguments. The summary is one aggregation rather than a sum over pages, so it covers every matching run. It sums `costUsd` only over runs that carry one and reports how many did as `pricedRuns`, because a run the provider could not price is unknown rather than free.

**The listing carries no answer, transcript, or error text**, which is what keeps it `internal`. The summary returns only counts, totals, timestamps, and one run id, so it is `internal` too. **The transcript read is `secret`** because a stored answer or tool result can hold a secret value, the same reason the history routes refuse the service token (see the read-path table under [Admin REST API](#admin-rest-api)). Because a read tool ships enabled, deploying it adds a private-data leg to the trifecta banner. Disable it on the Registry tab if the deployment does not need it.

`responseText` is returned only for a turn with no transcript, because the answer is already in the transcript's text segments. Every text field is cut to 20,000 characters. `toolAllowlistKnown: false` marks a record written before the allowlist was stored, which must not be read as unrestricted. Lookup by run id uses `AiQueryHistoryService.get(id)`, added for this tool.

**The transcript read is paged.** One agentic run can hold several hundred thousand characters, far more than one tool result should put into a caller's context, so a page carries about 120,000 characters of text. Each turn takes one position for its text fields and one per transcript segment, numbered across the whole response. The text fields always come first, so a turn's prompt and its expansion arrive before its transcript spends the page. Before taking each item the tool checks it fits in what is left of the page; when it does not, the page ends and `next` names that item's position, so no item is cut by the page total and the next call returns it whole. A caller repeats with `start: next` until `next` is `null`. A turn whose text fields arrived on an earlier page comes back with `continued: true` and without them. Pages are stable because a finished run's record never changes. A conversation longer than 50 turns is still cut at 50 and marked `turnsTruncated`.

### Tool-Invocation Tool

One built-in AI tool reads the audit trail in `module_ai-tools_invocations` through `ToolAuditStore.list()`. It is a read, ships enabled, and sits in the `ai-tools` group on the Registry tab.

| Tool | Class | Input | Returns |
|---|---|---|---|
| `ai-list-tool-invocations` | `secret`, surfaces untrusted content | All optional: `toolName`, `status`, `triggerPath`, `queryId`, `conversationId`, `since` and `until` (ISO 8601, bounding `createdAt` inclusively), `limit` (default 25, at most 100), `offset` (at most 100,000) | `total`, `offset`, `limit`, `returned`, `nextOffset` (`null` on the last page), and `invocations[]` newest first: `id`, `createdAt`, `toolName`, `providerId`, `aiProviderId`, `capability`, `triggerPath`, `actorKind`, `actorId`, `endUserId`, `clientId`, `queryId`, `conversationId`, `toolUseId`, `status`, `durationMs`, `costUsd`, `input`, `inputTruncated`, `resultDigest`, `error`, `screen` |

**It is `secret` because the audit trail is not redacted enough to be anything else.** The governor replaces a `secret` tool's argument values with `[redacted]`, but it stores every result digest as it came back, including a secret tool's, and it stores a non-secret tool's arguments verbatim, which can carry a secret variable's value a model chose to pass. Like `ai-get-prompt-run`, the tool therefore fails the MCP safety floor and adds a private-data leg to the trifecta banner while enabled. Disable it on the Registry tab if the deployment does not need it.

**Two stored fields are left out.** `errorRaw` is the upstream error body kept for admin forensics. Of `origin`, only `clientId` is returned: the caller's IP address and credential id stay on the admin Activity tab.

**An `ok` status only means the handler returned.** A tool that reports its own failure in its answer, such as `tronrelic-fetch-url` returning an HTTP 404, is recorded `ok`, so the reason is in `resultDigest`, the first 500 characters of the result. Arguments longer than 2,000 characters of JSON come back as a cut string marked `inputTruncated`; the full arguments and result are in the run's transcript from `ai-get-prompt-run`, matched by `toolUseId`.

**`queryId` joins a call to its run.** Every query path passes its history record id to the provider as `IAiQueryOptions.queryId`, and the governor stamps that id on each audit record, so the `id` `ai-list-prompt-runs` reports finds the run's calls here. The streaming route always did this, because its client-minted id is both. `executeSavedPrompt` and the non-streaming route used to mint the history id separately and pass none, so their audit records carry no `queryId` up to the deployment that fixed it; filter those older runs by `conversationId`.

`since` and `until` are parsed and rewritten in `toISOString()` form before they reach the store, because `createdAt` is stored as that string and `ToolAuditStore.list()` compares the bounds as strings. The store accepts the same two fields for any other caller.

### Saved Prompts & Triggers

Saved prompts are durable, **provider-independent** user assets — a named prompt body, optionally carrying autonomous **triggers** — owned by core so they outlive any provider swap (a plugin-scoped copy would be orphaned when the transport is disabled). `SavedPromptsService` owns `module_ai-tools_prompts` (`ISavedPrompt`) with atomic field-level writes; each prompt is its own document keyed by `id`, indexed unique `{ id }`, case-insensitive-unique `{ name }`, and descending `{ updatedAt }`. The `/query/prompts*` routes back the Query tab's prompt editor.

**The Query tab's chat card *is* the editor.** There is no separate saved-prompt panel or edit modal: the library is a dropdown in the chat header, and selecting a prompt starts a fresh chat and loads that prompt into the card's own controls — body into the composer textarea, `providerId`/`model` into the composer's provider-grouped model picker, `toolAllowlist` into the composer's tools dropdown, and `triggers[]` into a Triggers panel that opens above the composer. An editing strip labelled "Editing prompt" sits directly above the composer while a prompt is loaded, so the mode is visible beside the field whose behaviour it changes. One Save writes the whole document, so the surface an operator tests a prompt in is the surface they edit it in. Three consequences the client enforces: sending does **not** clear the composer while a prompt is loaded (the text is the body, and clearing it would empty what Save writes); the tool selection is sticky rather than one-shot for the same reason; and `toolAllowlist`'s three-state contract survives, because the editor pre-fills the enabled set for *display* only and tracks whether the operator really engaged the picker, so an untouched save sends `null` (all enabled, auto-updating) instead of freezing today's set. The model picker spans every registered provider so a prompt can pin a model on a non-active one — an interactive send runs on the active provider, so such a pin is deliberately not forwarded as that message's model override and the UI says so.

A prompt's firing rules live in a unified `triggers[]` discriminated array (`ISavedPromptTrigger`): `kind: 'cron'` elements evaluate on the scheduler tick, `kind: 'hook'` elements bind to a declared observer seam (the module's bindable allowlist — today `content.published`, optionally filtered by the payload's `typeId`, e.g. `blog:post`). Each element carries a stable server-assigned `id`, its own `enabled` flag, and its own run bookkeeping (`lastRunAt` / `lastRunError` / `failureCount`), written by array-filtered updates so two triggers on one prompt never clobber each other. An update replaces the array with a bookkeeping-preserving merge by trigger id — an edited cron re-anchors to now, a re-enable resets its failure streak. Migration `module:ai-tools:001_saved_prompt_triggers` folds the pre-triggers flat `cron`/`scheduleEnabled` schema into one cron element; the Conversation card's Triggers section edits the array directly (`GET /query/prompts/hooks` lists the bindable seams for its hook picker), and the legacy flat body fields and read-time projection are gone. Because Save sends the complete replacement set, every row is transmitted on each write — including untouched ones — and each row carries its server-assigned `id` so the merge preserves that element's run bookkeeping rather than re-anchoring its cron.

**Hook firing is enqueue-only.** The hook fires in-process during another pipeline's commit (curation's decision commit), so the module's `content.published` subscription only looks up bound prompts (`listHookBound`), applies each trigger's `typeIdFilter`, and enqueues a job on the durable BullMQ `ai-tools:hook-prompts` queue — never awaiting the AI call inline. The worker re-reads the prompt fresh, drops the job if the binding no longer holds, claims the run, and executes through the same shared `executeSavedPrompt` path as the cron runner, with the hook payload substituted as per-run `{%hook.*%}` variables (`hook.type-id`, `hook.ref`, `hook.descriptor`, `hook.title`, `hook.body`) — per-run values never enter the shared prompt-variable registry. The queue factory is injected by bootstrap; without it (tests, Redis-less boots) hook triggers are editable but inert.

A prompt also carries an optional **`toolAllowlist`** — the least-privilege set of tools it may call. Three-state: absent = every tool currently switched on, `[]` = no tools, a name list = that subset (intersected with the enabled and autonomous-allowed sets at fire time; a listed name resolving to no tool at all fails the run and counts toward auto-pause). Entries are validated non-empty and un-padded on save (a blank or whitespace-wrapped name never matches a real tool). The composer's tools dropdown doubles as the editor for this field: it pre-fills everything switched on for a prompt that carries no explicit list — least privilege is opt-in narrowing — and shows a per-run trifecta badge (`POST /trifecta/preview`) that recomputes as the selection changes. With no prompt loaded the same dropdown is an ordinary one-shot grant, defaulting to no tools and clearing after each send. The scheduled runner forwards the stored allowlist into `getActive().query({ ... })` so an autonomous run is scoped to it.

**The list names provider-hosted tools too.** An entry carrying the reserved `hosted:` prefix (`hosted:web_search`) grants one of the vendor-hosted tools the active provider reports through `IAiProvider.listActiveServerTools(model)`; `splitToolAllowlist` from `@delphian/tronrelic-types` separates the two halves, and `AI_TOOL_NAME_PATTERN` forbids a colon in a registry tool name, so the two can never be confused. The prefix carries no provider id, because a grant means "this run may search the web" rather than "this run may use Anthropic's search", and so survives a provider swap.

The two halves are enforced in different places, and the difference is the point. A registry tool is filtered out of the advertised set for accuracy and re-checked at `governor.invoke()`, so the governor is the real gate. A hosted tool never reaches the governor — the vendor runs it — so leaving it out of the request's `tools` array *is* the gate, and the provider is where it happens. The grant only narrows either way: a hosted tool the provider config has switched off for the run's model stays off however the allowlist names it, and a `hosted:` name the provider does not host fails the run the same way a missing registry tool does. A hosted name that exists but is switched off is filtered, not fatal, mirroring a registered-but-disabled registry tool.

Because no allowlist written before the prefix existed can contain a `hosted:` entry, every stored prompt reads as granting no hosted tools. That is a deliberate tightening on upgrade: a prompt that had been getting web search only because the model-level switch was on now runs without it until an operator grants it, since a grant nobody made is not a grant.

`ai-tools:run-scheduled-prompts` evaluates every enabled cron trigger on each 2-minute tick (`runScheduledPrompts`). A due trigger is **claimed before it fires** — `lastRunAt` is written first — so a slow query can never double-fire on the next tick (worst case is a skipped run on crash, never a duplicate). The run executes through `getActive().query({ mode: 'programmatic' })`, which the provider attributes as `triggerPath: 'programmatic'` / `actor: system`; the governor's external-tool default-deny keys on `triggerPath !== 'interactive'`, so an autonomous run gets the same protection a dedicated `scheduled` path would — the public `IAiQueryOptions` deliberately carries no trigger field, which keeps any caller from claiming `interactive`. With no provider installed the tick is a no-op and prompts wait untouched. Five consecutive failures auto-pause the firing trigger (`enabled: false`) with an annotated `lastRunError`; any success, cron edit, or re-enable resets that trigger's streak. **Only a thrown query counts as a failure for the streak.** A run that returned without answering is recorded as `incomplete` and logged at `warn`, but it resets the streak like any other returned query, so a prompt that reliably produces nothing keeps firing rather than auto-pausing. That is deliberate: auto-pause exists for a prompt that is broken, and a truncated or refused run usually reflects a budget or a wording an operator should fix rather than a schedule that should stop. Each run (success or failure) is also recorded in `module_ai-tools_query_history` tagged `mode: 'scheduled'`, each with its own `conversationId` so the grouped Query-tab history surfaces it (records without one are hidden one-shots) — an autonomous run is visible beside interactive queries, badged `Scheduled`.

**Manual run-now.** The editing strip's ▶ button executes the loaded prompt on demand through `POST /query/prompts/:id/run` (session-only — it expands registry tokens like any query). It runs the same shared `executeSavedPrompt` path as the cron and hook firings — programmatic mode, the re-resolved owner principal, the prompt's injected system prompt and three-state tool allowlist, one history row badged `scheduled` — but carries **no `triggerId`**, so it keeps no failure streak and can never auto-pause a schedule (`triggerId`/`claimedAt` are optional on `ISavedPromptExecutionOptions`; all trigger bookkeeping is skipped when absent). The route validates upfront (the prompt exists and a provider can run it) so the operator gets an immediate error, then **fires the run without awaiting it** — an autonomous query can take minutes — returning `202` with the `conversationId` the result will be recorded under. The controller mints that id and passes it through `ISavedPromptExecutionOptions.conversationId`, so the Query tab's toast can offer to open the result: the chat shows the run as in progress and polls the conversation until its history row lands. The module exposes this as `runSavedPromptNow(promptId, conversationId?)`, and both it and the hook worker build their collaborators through one shared `buildSavedPromptExecutionDeps()` so the firing paths cannot drift.

### Saved-Prompt Tools

Two built-in AI tools read the library through `SavedPromptsService.list()`. Both are `read` / reversible / `internal`, ship enabled, and sit in the `ai-tools` group on the Registry tab beside the prompt-variable tools.

| Tool | Input | Returns |
|---|---|---|
| `ai-list-saved-prompts` | none | `total`, `returned`, `truncated` (more than 500), and `prompts[]` newest-updated first: `id`, `name`, `providerId`, `model`, `toolAllowlist` (`null` = every enabled tool), `ownerUserId`, timestamps, `promptChars`, and `triggers[]` with `lastRunFailed` and `failureCount` but no error text |
| `ai-get-saved-prompts` | `prompts`: 1–10 ids or names (names match case-insensitively, as the unique index does) | `prompts[]`, one per reference: `ok` with the same settings, the body as `prompt` (cut to 20,000 characters, with `promptChars` and `promptTruncated`), and `triggers[]` including `lastRunError` (cut to 2,000 characters); or `not-found` with a reason |

The body is returned as the stored template, so a `{%name%}` token is never expanded and a `secret` variable stays a token. That is why both tools can be `internal`: secrets belong in variables, not in prompt bodies. `ownerLabel` is never returned, because it is usually an admin's email address and these tools can be granted to MCP users; `ownerUserId` is. The read tool declares `surfacesUntrustedContent`, because `lastRunError` can carry text from an AI provider's error response. The listing leaves that text out so it does not need the flag.

### System Prompts

Core-owned, provider-neutral system prompts injected into every query. `SystemPromptsService` (internal — not on the registry) owns one always-on **master** prompt (core `_kv` key `ai-tools:system-prompt-master`, may be blank) plus any number of audience-scoped **additional** prompts (`module_ai-tools_system-prompts`, indexed unique `{ id }` and `{ order }`). Each additional prompt targets `userIds` (any-of) and/or `groups` (all-of); it applies when the querying user's id is in `userIds` **OR** the user is a member of every listed group — the two filters combine with **OR**. A both-empty additional prompt is rejected (the master covers everyone). Bodies expand `{%name%}` variables.

`compose(principal)` assembles the master first, then each enabled matching additional prompt by ascending `order`, then `{%name%}`-expands the whole via the prompt-variable registry — returning `''` when nothing applies. Both core query call sites compose and pass the result as `IAiQueryOptions.injectedSystemPrompt`: the interactive query controller (matching the admin's resolved `endUser`) and the scheduled-prompts runner (matching the prompt owner's re-resolved principal; a null principal yields master-only). The active provider injects it **after** its always-on security clause and **before** its own `config.systemPrompt`, so the final `system` order is **security clause → core injected → provider config** — core's prompts and the provider's own coexist rather than one replacing the other. A compose failure degrades to no injection rather than failing the query.

## Hook Seams

Declared in `src/backend/hooks/registry.ts`. `ai.toolInvoke` (series, `IAiToolInvokeContext`) fires before execution — throw `HookAbortError` to block; lets a compliance or lethal-trifecta plugin veto without forking the provider. `ai.toolResult` (waterfall, `IAiToolInvokeContext`) fires after the handler returns and before the provenance wrap and untrusted-content screen — a handler threads the raw result to alter it (redact / reshape / summarize) or throws `HookAbortError` to withhold it from the model, while the raw result is still digested into the audit record. `ai.toolInvoked` (observer, `IToolInvocationRecord`) fires after, for audit fan-out and alerting. All three surface on `/system/hooks`.

## Lifecycle Obligations

`init()` constructs the registry, policy engine, audit store, approval queue, governor, provider registry, query-history service, saved-prompts service, prompt-variable registry (into which it registers the core-owned built-in dynamic variables), and system-prompts service; loads persisted tool-states, policy overrides, and prompt-variable statics + classifications; ensures every collection's indexes (the collections are new, so index creation here is correct rather than a migration — including `module_ai-tools_query_history`, `module_ai-tools_prompts`, `module_ai-tools_variables`, and `module_ai-tools_system-prompts`); and `watch`es the registry for `'curation'`, injecting `policy.setCurationResolver(curation.hasType)` while it is present and re-tightening to deny-all if it unregisters. `run()` mounts the admin router, registers `'ai-tools'` / `'ai-tool-governor'` / `'ai-providers'` / `'prompt-variables'`, wires the governor's broadcast sink to `WebSocketService`, registers the daily `ai-tools:prune-audit` retention job and the 2-minute `ai-tools:run-scheduled-prompts` job (both only when a scheduler is injected), and registers the `/system/ai-tools` admin nav item under the System container. Errors in either phase fail the boot — there is no degraded mode.
